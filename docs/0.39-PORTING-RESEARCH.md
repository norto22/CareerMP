## Headline conclusion

"Almost starting from scratch" is true of the *game's* career code, not of CareerMP.

CareerMP forks 10 game files totalling ~6,600 lines, but its **actual intent across all
of them is ~136 changed lines**, and most of those are one-line `extensions.hook(...)`
argument additions. The port is not a rewrite — it is:

1. Re-fork 10 files from 0.39 pristine and re-apply ~136 lines. *(mechanical)*
2. Fix 8 hard-broken API calls. *(small, known)*
3. Rewrite the top-bar patch against the new UI stack. *(genuinely new work)*
4. Optionally delete ~1,500 lines of drag-race code by using 0.39's **native, dormant
   multiplayer drag support**. *(big win — see below)*

so they re-apply cleanly.

## Breaking changes in 0.39

### 1. Save system: `saveSlot` → `profile` (the big one)

Every save-slot symbol was renamed, and saves gained a profile/folder split
(the patch notes' "save/load multiple manual saves for each profile").

`career_saveSystem`:

| 0.38.6 | 0.39 |
|---|---|
| `setSaveSlot` | `setProfile` |
| `getCurrentSaveSlot` | `getCurrentProfile` |
| `getAllSaveSlots` | `getAllProfiles` |
| `removeSaveSlot` | `removeProfile` |
| `renameSaveSlot` | `renameProfile` |
| `getAllAutosaves` | `getAllSaveFolders` |
| `getAutosave` | `getNewestSave` |
| — | `getCurrentDisplayName`, `removeSaveFolder` (new) |

`career_career`: `sendAllCareerSaveSlotsData`→`sendAllCareerProfilesData`,
`sendCurrentSaveSlotData`→`sendCurrentProfileData`,
`getAutosavesForSaveSlot`→`getAutosavesForProfile`, plus new `getSaveFoldersForProfile`.

Hooks renamed: `onSetSaveSlot`→`onSetProfile`, `onBeforeSetSaveSlot`→`onBeforeSetProfile`,
`onSaveCurrentSaveSlot`→`onSaveCurrentProfile`,
`onSaveCurrentSaveSlotAsyncStart`→`onSaveCurrentProfileAsyncStart`.

Save format: `saveSystemVersion` 61 → **64**; `backwardsCompVersion` stays **36**, so
0.38.x career saves still load.

#### Profile names are now sanitised — affects CareerMP directly

`saveSystem.lua:103` `getSanitizedProfileName()`:

```lua
local sanitizedName = string.lower(profileName or '')
sanitizedName = string.gsub(sanitizedName, '[^a-z0-9]', '')
if sanitizedName == '' then sanitizedName = 'profile' end
-- then de-duplicates against existing local profiles: name, name1, name2...
```

CareerMP names the save after the BeamMP nickname. In 0.39 the *folder* becomes
lowercase-alphanumeric-only, with the original kept separately as `displayName`.
Two consequences:

- Nicknames differing only in punctuation/case collide (`Player_1` and `player1` →
  both `player1`).
- The de-dup counter is evaluated against *that client's* existing profiles, so the
  same nickname can map to `player` on one machine and `player1` on another. This
  weakens the "same save across any CareerMP server" guarantee.

Sanitisation only runs when no `info.json` exists (i.e. creating a new profile), so
existing profiles are stable. CareerMP 0.39 should sanitise the nickname itself,
deterministically, and pass that — never rely on the game's de-dup counter.

### 2. Career start signature changed

```lua
-- 0.38.6
createOrLoadCareerAndStart(name, specificAutosave, tutorial)   -- 3rd = boolean
-- 0.39
createOrLoadCareerAndStart(name, specificAutosave, startingOptions) -- 3rd = table
```

New `startingModes/` system. Available modes:

| id | title | visible |
|---|---|---|
| `apmOnboarding` | APM Onboarding | yes (major) |
| `freshStart` | Open World | yes (minor) |
| `selfMade` | Self-Made | `ignore = true` |
| `sandbox` | Sandbox ($50M, all unlocked) | `ignore = true` |

`M.tutorialEnabled` is now *derived*: `startingOptions.startMode == "apmOnboarding"
and not careerData.boughtStarterVehicle`, and it force-disables autosave.

CareerMP's old call passed `false` as the 3rd argument. That does not error (non-table
→ `{}`), but it leaves `startMode` unset, so no starting mode initialises the profile.
**`freshStart` is the correct default for multiplayer** — it matches the old behaviour
of skipping onboarding, and avoids running a scripted tutorial in a shared world.

`linearTutorial.lua` was **deleted**, replaced by `tutorial.lua`, `tutorialPopups.lua`
and a 9-step `tutorial/` directory. `career_modules_linearTutorial.isLinearTutorialActive()`
— called by the mod's `getAdditionalMenuButtons` — no longer exists.

### 3. `ui_topBar` deleted — UI overhaul

`lua/ge/extensions/ui/topBar.lua` and `ui/topBar/` are **gone**. So is
`gameplayAppContainers.lua`, `messagesTasksAppContainers.lua`, `vehicleVicinityApp.lua`.

New UI stack: `menuManager.lua`, `router.lua` (856 lines), `uiStateManager.lua`,
`appContainers.lua`, `appLayouts.lua`, `pause/` (with `providers/`, `features/`),
`garage/`, and per-gamemode selectors. `menuManager` exposes `openMenu`, `closeMenu`,
`toggleMenu`, `closeToMenu`, `menuHide`, `setGameplayRoute`, `isPauseV2Enabled`.

CareerMP's `patchTopBar()` — which removed the `environment` / `mods` / `vehicleconfig`
/ `vehicles` entries — **will hard-error**. This is the one part with no mechanical
translation; the entry list now lives behind the router/pause-V2 layer.

### 4. UI app layout API changed (layout *files* survive)

- `ui_apps.requestUIAppsData()` → **gone**. Nearest equivalent:
  `ui_apps.notifyLayoutsChanged()` (fires the `UiAppLayoutsChanged` guihook).
- `ui_apps.getAvailableLayouts` / `isAppOnLayout` / `saveLayout` / `deleteLayout` →
  moved to `ui_appLayouts` (`addApp`, `removeApp`, `setCurrentLayout`, `saveLayout`, …).
- App show/hide → `ui_appContainers` (`showApp`, `hideApp`, `setAppVisibility`,
  `registerContainer`).

Good news: `settings/ui_apps/originalLayouts/{default,mission}/*.uilayout.json` still
exist in the same place with the same schema, and 0.39 now *watches* layout files and
auto-refreshes (debounced `onFilesChanged`), so CareerMP's write-the-json approach
still works. Layout roster changes: `gravityRace` added (default);
**`rallyModeRecce` removed (mission)** — drop it from the mod's `missionLayouts` table.

### 5. Insurance: mod's patches now partly obsolete, and one shape assumption is wrong

The `deductible` field changed shape. 0.39 `insurance.lua:481`:

```lua
local deductibleValue = costs.deductible
if type(deductibleValue) == "table" then
  deductibleValue = (deductibleValue.money or 0) + (deductibleValue.vouchers or 0)
```

`.money` / `.vouchers` are now **numbers**. CareerMP's 0.38.6-era patch reads
`deductible.money.amount` / `deductible.vouchers.amount` — i.e. it treats them as
tables. Carrying that patch forward would break. 0.39 also normalises the value before
writing history (`deductible = deductibleValue or 0`), so the matching patch in
`history.lua` is dead code too.

**Drop both deductible patches.** 0.39 handles it natively, and also added legacy-save
recovery (`insurance.lua:347-352`, coercing `nil` `insuranceId` to `-1`) — the
save-corruption fix from the patch notes.

**Still keep** the mod's other insurance fix. `insurance.lua:460` in 0.39 reads:

```lua
local insuranceId = invVehs[invVehId].id      -- inventory id used as an insurance id
```

CareerMP corrects this to `.insuranceId`. The bug is **still present upstream in 0.39**
and worth reporting to BeamNG.

### 6. Traffic setup path changed

0.39's `activateCareer` now does:

```lua
freeroam_freeroam.resetSpawningOptions()
freeroam_freeroam.spawningOptionsHelper.trafficMode = "disabled" -- career_playerDriving will manage traffic setup
```

CareerMP's `playerDriving.lua` fork drives traffic counts from server config
(`roadTrafficAmount`, `parkedTrafficAmount`, `extraTrafficEnabled`, …). That still
works, but it now interacts with the new spawning-options helper, and
`initAfterLevelLoad` is **deferred** via `pendingInitAfterLevelLoad` instead of being
called straight from the level-load callback. Needs testing, not rewriting.

Also new in `activateCareer`: `core_gamestate.requestEnterLoadingScreen('careerActivate')`
/ `requestExitLoadingScreen` gating.

## The big opportunity: 0.39 ships dormant native multiplayer

0.38.6 had **zero** files mentioning `isMultiplayer`. 0.39 has **14**, plus references
to a whole `multiplayer_*` extension family that the game does not itself ship:

`multiplayer_sessionManager` (25 refs), `multiplayer_settings` (10),
`multiplayer_nametags` (8), `multiplayer_multiplayer` (8), `multiplayer_vehicleSync` (5),
`multiplayer_synclib` (5), `multiplayer_gameplayScoreboard` (3),
`multiplayer_gamemodes_utils_spectator` (2).

Also new: `freeroam/configuratorOptions/mpOptions.lua` (session options — local session,
`maxPlayers` up to 64, ghost-on-teleport/reset, vehicle collisions, allow pausing),
`ui/pause/providers/routeData/multiplayer.lua`, `ui/router/routes/multiplayer.lua`,
`gameplay/drift/multiplayer.lua`, `core/settings/multiplayer.lua`.

BeamNG is clearly building first-party multiplayer. Two implications:

**Opportunity — drag racing sync is already written.** `gameplay/drag/display.lua` in
0.39 contains full MP logic: `getNetworkTimersForVehicle(vehId)`,
`updateTreeLightsFromNetwork(lane, lightState)`, host-broadcasts-tree-lights, and
"in MP, skip UI updates for remote racers entirely". It is gated on one stub —
`core.lua:31`:

```lua
local function getDragGamemode()
  -- Restore the two lines below once multiplayer drag is ready to ship.
  -- local ext = _G[DRAG_MP_GAMEMODE_EXT]
  -- if type(ext) ~= "table" then return nil end
  -- return ext
  return nil
end
```

`DRAG_MP_GAMEMODE_EXT` = `extensions.luaPathToExtName('multiplayer/gamemodes/drag/drag')`
→ `multiplayer_gamemodes_drag_drag`.

So CareerMP 0.39 can ship
`lua/ge/extensions/multiplayer/gamemodes/drag/drag.lua` and monkey-patch
`gameplay_drag_core.getDragGamemode` to return it. The game's own code then drives
the tree, timers, scoreboard and remote-racer UI suppression — replacing
`display.lua`'s 1022-line fork (1230 lines of drift) **and** the 473-line
`careerMPDragDisplays.lua`. Roughly 1,500 lines deleted for one ~25-function shim.

Interface the game expects from the gamemode object (25 symbols, harvested from all
39 `getDragGamemode()` call sites):

```
isMultiplayer  isServerHost  getLocalPlayerId  getPlayerIdByClientId
getRaceState  getActiveDragRace  getLocalClientActiveRace  clearLocalClientActiveRace
getRaceStartTime  getCountdownStartTime  notifyRaceStart  checkTimerDrift
updateTimerValue  syncTreeLightState  syncStageLightState  shouldSyncState
broadcastRulesUpdate  getSynchronizedRandValue  onDragRaceListChanged
isMenuOpen  openMenu  setMenuState  setContext  dragType  treeType  util
```

Not all 25 are needed for a first pass — `isMultiplayer`, `getLocalPlayerId`,
`getRaceState` and the sync/notify calls carry most of the behaviour.

**Risk — namespace collision.** BeamMP's client mod *is* `multiplayer_multiplayer`.
0.39 game code now probes `multiplayer_multiplayer` and `multiplayer_settings`
expecting its own API shape (e.g. `multiplayer_settings.extraOptions.ghostOptions`).
CareerMP already monkey-patches `multiplayer_multiplayer.onUpdate`. Expect
interference, and treat any game code path that probes `multiplayer_*` as suspect
until tested. Most of it is `shipping_build`-gated (`mpOptions.lua` returns early on
shipping builds), which limits the blast radius for now.

## How CareerMP worked (architecture reference)

This section describes **0.0.37 as it was**, on 0.38.5. It is kept because the event
protocol, join flow and vehicle active-state sync carried over to this port essentially
unchanged, and because it documents what the forks were actually for. The file layout
below is the old one — see the outcome table above for what replaced each fork.

### Layout

```
Resources/
  Client/CareerMP.zip                 ← client mod, auto-fetched by server
  Client/CareerMP/
    scripts/CareerMP/modScript.lua    ← entry: load()s 7 extensions, unloadMode 'manual'
    lua/ge/extensions/
      careerMPEnabler.lua             ← core: config, veh state sync, settings, patches
      career/careerMP.lua             ← fork of career.lua, REPLACES global career_career
      career/modules/*.lua            ← forks of 6 career modules
      gameplay/walk.lua               ← fork
      gameplay/drag/display.lua       ← fork
      careerMPDragDisplays.lua        ← drag tree/scoreboard sync
      careerMPPrefabSync.lua          ← mission prefab sync
      careerMPUIApps.lua              ← injects MP apps into UI layouts
      careerMPPerPartPaint.lua        ← per-part paint sync
      careerMPPlayerPayments.lua      ← player-to-player payments
    lua/vehicle/extensions/auto/careerMPEnabler.lua  ← vehicle-side ghost/visibility
    ui/modules/apps/CareerMP-PlayerList/             ← custom player list app
    levels/west_coast_usa/...                        ← garage/dragrace trigger tweaks
  Server/CareerMP/careerMP.lua        ← BeamMP server plugin
```

### The override strategy

Two distinct mechanisms:

1. **Shadow-fork.** The client mod ships files at the *same paths* as game files, so
   the mod's copy wins. Used for the 9 game-file forks. Fragile: every game update
   invalidates them, and the intent is invisible without a 3-way diff.
2. **Namespace swap.** `career/careerMP.lua` is a *renamed* fork loaded as
   `career_careerMP`, then `careerMPEnabler.onExtensionLoaded` does
   `career_career = extensions.career_careerMP`, globally replacing the career module.

### Client → server events

`careerSyncRequested`, `careerVehSyncRequested`, `careerVehicleActiveHandler`,
`prefabSyncRequested`, `careerPrefabSync`, `perPartPainting`, `requestPartPaints`,
`payPlayer`, `speedTrap`, `redLight`, and 9 drag `tx*` events
(`txUpdateDisplay`, `txUpdateWinnerLight`, `txUpdateBlueLight`, `txUpdatePreStageLight`,
`txUpdateStageLight`, `txUpdateDisqualifiedLight`, `txUpdateTreeLights`,
`txClearDisplay`, `txClearAll`).

### Server → client events

`rxCareerSync` (client config + triggers career start), `rxClientConfigUpdate`,
`rxCareerVehSync` (authoritative vehicle active-state map), `rxTrafficSignalTimer`
(10 s broadcast), `rxPrefabSync`, `rxRemotePartPaint`, `rxRequestPartPaints`,
`rxPayment` / `rxConfirmation` / `rxBounce` / `rxDeny`, and the 9 `rx*` drag mirrors.

### Join flow

1. `onWorldReadyState(2)` → client fires `prefabSyncRequested` + `careerSyncRequested`.
2. Server replies `rxCareerSync` with `Config.client`.
3. Client applies traffic/gameplay settings and input-action blocks, then calls
   `career_career.createOrLoadCareerAndStart(nickname .. suffix, false, false)`.
4. Server marks `pendingActivation[id].careerActive = true`.
5. Server-side watchdog drops any player who hasn't activated within **90 s**
   (`activationThreshold`), on a 1 s `tick`.

### Vehicle active-state sync (the load-bearing mechanism)

Career constantly hides/shows vehicles (garage, shopping, missions). Locally hidden
vehicles must be hidden for everyone, so:

- `onVehicleActiveChanged` → owner sends `{serverVehicleID, active}`.
- Server keeps `vehicleStates[player_id .. "-" .. vehicle_id]` and broadcasts the whole
  map on every change.
- Receivers `setActive(0/1)` on non-owned vehicles and set `hideNametag`.

Nametag suppression uses a hardcoded 80-entry `hiddens` model list (props, trailers,
`simple_traffic`, etc.). Render distance is forced to `1610` so players are visible on
the big map.

### Server plugin

Pure BeamMP API (`MP.*`, `Util.*`, `FS.*`) — **touches no game Lua, so it is
version-agnostic and ports as-is.** Contains: JSON config with self-healing
(adds missing keys, strips unknown ones), self-update from GitHub raw via
`Invoke-WebRequest`/`wget`, console command parser (`CareerMP <cmd>` / `CMP <cmd>`),
rate-limited payment ledger (short/long window + session caps), speed-trap and
red-light notification broadcasting, and a 7-entry speed-trap location name table.

### Other notable bits

- `computer.lua`: tether range widened 4 m → **25 m** (sphere and box) so MP latency
  doesn't eject players from garage computer menus.
- `computerMenuHandler` is bound to four hooks (`onCareerTuningStarted`,
  `onPartShoppingStarted`, `onPerformanceTestStarted`, `onVehiclePaintingUiOpened`) —
  this is *why* the mod forks those modules: it needs the hooks to carry a vehicle id.
- `walk.lua`: unicycle search gains an `MPVehicleGE.isOwn()` guard, and the career
  unicycle config becomes `vehicles/unicycle/beammp_default.pc` instead of
  `without_mesh.pc` (the `.pc` ships with the BeamMP client, not this mod).
  0.39 deleted the all-vehicles scan this guard protected, so only the config change
  survives — and it no longer needs a fork.
- `modifiedGetDriverData` inspects `debug.getinfo(2).name == "getDoorsidePosRot"` to
  flip driver side for remote (`mpVehicleType == 'R'`) vehicles — a fragile
  call-stack-sniffing hack worth replacing.
- Requires `MaxCars = 100`+ and `Map = "/levels/west_coast_usa/info.json"`.
  Career is West Coast USA only.

## Recommended architecture change

The old mod's central weakness is the shadow-fork: ~6,600 lines copied to change ~136,
with no markers, so every game update means re-forking blind.

**Replace shadow-forks with runtime monkey-patching wherever the change is additive.**
Nearly all of the mod's intent is "call `extensions.hook` with an extra argument" or
"change one constant". Both are expressible as a wrapper installed at load time:

```lua
-- instead of forking 1031-line partShopping.lua to change 3 hook calls:
local orig = career_modules_partShopping.startShopping
career_modules_partShopping.startShopping = function(...)
  local r = orig(...)
  extensions.hook("onPartShoppingStarted", getCurrentVehicleVehId(), currentVehicle)
  return r
end
```

Patches survive game updates, break loudly and locally when they don't, and make the
mod's intent self-documenting. Where a *local* function or upvalue must change
(e.g. `computerTetherRangeSphere`), a narrow fork is still the only option — but that
is 1–2 files, not 10.

What was built:

1. `careerMP/compat.lua` — one place mapping every renamed 0.39 API, so a future rename
   is a one-file fix. Logs anything it cannot resolve.
2. `careerMP/patches.lua` — the runtime wrappers, replacing seven forks.
3. `careerMP/careerPatches.lua` — replaces the `career.lua` fork.
4. `multiplayer/gamemodes/drag/drag.lua` + `careerMP/dragSync.lua` — native MP drag.
5. Narrow forks kept only for `computer.lua` and `playerDriving.lua`.

Two things learned the hard way while building this, both worth knowing if you attempt
something similar:

**Wrap direction matters.** `startShopping`, `tuning.start` and `painting.start` all call
their `*Actual` function synchronously, and *that* is what fires the stock hook. A
post-call wrapper therefore records the vehicle only after the hook it was meant to
inform has already fired. These need pre-call wrappers. The symptom was subtle: part
customization silently stopped seating the player in their vehicle, so edits no longer
synced, with no error anywhere.

**Give every patch module a load hook.** `patches.lua` originally installed its wrappers
only from `onCareerActive`, and had no `onExtensionLoaded` and no logging. When that hook
did not reach it, the wrappers were never installed and there was no trace of it in the
log at all — the module simply did nothing, silently. Log at load, log on apply, and
retry from `onUpdate` until the target modules exist.

## Test status

Developed against the game trees, first run on 0.39.1 with an unofficial 0.39-capable
BeamMP build while no official one existed, then re-verified on BeamMP's own 0.39 release,
and most recently on **0.39.2.1 (build 20887)**. The drag racing work below was done
entirely on 0.39.2.x.

Confirmed working in a live session: joining and having the career profile create and
load, buying a starter vehicle, part customization including being seated so edits sync,
and parcel deliveries.

**Drag racing is now exercised with two players**, on one strip, on west_coast_usa:
staging, a synchronised tree, the run, the result screen, and the strip clearing itself.
Also covered: solo runs, false starts (the run voids rather than stranding the strip), and
racing an AI bot in a BMRA mission with the multiplayer layer standing clear. The section
below records what that took — the interface was originally derived from the 39
`getDragGamemode()` call sites rather than a running implementation, and roughly a dozen
of the assumptions that produced were wrong.

Not yet exercised: tuning and painting menus, insurance and repairs, prefab sync, per-part
paint between players, and more than two players at once.

The `MPVehicleGE` / `MPCoreNetwork` / `multiplayer_multiplayer` surfaces may still shift
with BeamMP updates.

## Bugs found in the base mod

Latent in 0.0.37, surfaced by the port or by testing:

- `CareerMP-PlayerList/app.js` declared `pingList` with `let` at top level. 0.39's UI app
  service re-evaluates `app.js` in the same scope on refresh, so the second evaluation
  threw `Identifier 'pingList' has already been declared` and aborted the script before
  `.directive()` ran — the player list never registered at all. `var` is required here.
- `perPartPaint` pushed the inventoryId onto `pendingPaints` once per *non-matching* MP
  vehicle, so each spawn queued N−1 redundant retries and the queue grew without bound.
- `perPartPaint.onConditionCheckCallback` read `.paintData` off an entry that *was* the
  paint data, then called `table.remove(t, key)` on a hash-keyed table.
- The enabler queued `careerMPEnabler.setUnicycleGhost` / `setAllGhost` on vehicles.
  Neither exists on the vehicle side, and neither config key exists on the server — both
  calls errored in the vehicle VM and did nothing.
- Server: `if commandPrefix == "CareerMP " or "CMP " then` is always true, so every
  console line containing a space was parsed as a CareerMP command.
- `onPerformanceTestStarted` was bound by the enabler but is fired by neither 0.38.6 nor
  0.39, so the certification menu never seated the player.

## Multiplayer drag racing: what 0.39 ships and what is missing

Researched in full before implementation. 0.39 contains most of a working multiplayer
drag implementation; it is switched off only because `getDragGamemode()` is hard-wired
to `nil` (see above). What follows is the complete design as read from the source.

### The parts BeamNG already wrote

`gameplay/drag/mpDragHandlers.lua` (415 lines) implements the entire **receive** half of a
16-message protocol, and every apply-side entry point is exported from
`gameplay_drag_core`: `setRaceState`, `clearRaceState`, `setDragRaceData`,
`onDragRaceStart`, `onDragRaceCountdownStart`.

Race state shape:

```
raceState = {
  players         = { [playerId] = { vehicleId, configName, persona } },
  queue           = { [heatIndex] = { [lane] = playerId } },
  currentPairIndex, isStarted, treeType, creatorId, poiData, lobbyId,
  finishTimes     = { [playerId] = elapsed },        -- authoritative result
  timerValues     = { [playerId] = { [timerName] = value } },
}
```

`core.lua:1106` is the payoff — given `players` and `queue`, the game registers *every*
player in the current heat as a real racer:

```lua
local slot = queue[heatIdx]
for lane = 1, #dragData.strip.lanes do
  local playerId = slot[lane]
  if playerId and players[playerId] then
    setupRacer(players[playerId].vehicleId, lane)
  end
end
```

Single-player mode explicitly refuses this (`core.lua:819` wipes `racers` and registers
only `be:getPlayerVehicleID(0)`), which is why two players cannot currently race.

### The gamemode is the network adapter

The game calls gamemode methods at exactly the right moments; implementing them as sends
is most of the sender work. Mapping, with call sites:

| gamemode method | called from | emits |
|---|---|---|
| `syncStageLightState(raceId, lane, staged)` | `display.lua:1261,1297` | `dragRaceTreeLightUpdate` → host |
| `syncTreeLightState(raceId, lane, lights)` | `display.lua:251,254` | `dragRaceTreeLightUpdate` → host |
| `notifyRaceStart(raceId)` | `display.lua:662` | `dragRaceStart` → all |
| `updateTimerValue(raceId, vehId, name, val)` | `times.lua:131`, `dialPopup.lua:111` | `dragRaceTimerUpdateRequest` → host |
| `broadcastRulesUpdate(rules)` | `dragBridge.lua:510` | `dragRaceRulesUpdate` → all |
| `onDragRaceListChanged()` | `core.lua:1173` | race list broadcast |
| `getSynchronizedRandValue()` | `display.lua:674` | *reads* host's `randValue` |
| `checkTimerDrift()` | `times.lua:144` | host-only race advance |
| `shouldSyncState()` / `isServerHost()` | many | host gate |

The one sender BeamNG already wrote is the finish time, `phaseHandlers.lua:875`:
`mpsm.sendSessionHost("dragRaceFinishTime", { rawTime = os.clockhp() })`.

### Staging flow, end to end

1. Each client detects its own car staging locally (phase 1).
2. `syncStageLightState` → `dragRaceTreeLightUpdate` to the host.
3. Host's handler raises `onDragRaceTreeLights` → `core.setRacersInLaneStaged(lane, staged)`
   → `phaseHandlers.setRemoteStagingState`, which marks that lane staged after a **1 second
   hold** (matching single player).
4. Host re-broadcasts `dragRaceTreeLights` so other clients see the lights.
5. When all racers in the heat are staged, the host starts the countdown and broadcasts
   `dragRaceCountdownStart { startTime, randValue }` — the shared `randValue` is what makes
   every client's tree use the same delay.
6. `dragRaceStart { startTime }` advances everyone to the race phase.
7. Each client times **its own** car only, and sends `dragRaceFinishTime` to the host.
8. Host converts to its own clock, stores `finishTimes[playerId]`, and broadcasts
   `dragRaceFinishTimeBroadcast`. One authoritative result set, so one agreed winner.

### What CareerMP now implements

Built on top of everything above:

| file | role |
|---|---|
| `careerMP/dragTransport.lua` | the `bridge` (10 fns), the `state` table, routing into `mpDragHandlers.handle`, and loading that module -- **nothing in the base game loads it**. Also normalises the wire shape back into the maps the handlers expect |
| `careerMP/dragSync.lua` | activation, and the source rewrite that actually restores `getDragGamemode` (plus the `display.lua` message de-duplication) |
| `multiplayer/sessionManager.lua` | the 5 functions the game looks for; lets the shipped `phaseHandlers.lua:875` send its own finish times |
| `multiplayer/synclib.lua` | `mapOtherClock` -- race anchor plus lowest-RTT offset probing. Used for finish times, not the race clock |
| `multiplayer/gamemodes/drag/drag.lua` | the network adapter: the methods the game calls, turned into protocol messages. Also owns the host's stage advance, the result finalise, and the race teardown |
| `careerMP/dragLobby.lua` | presence, pairing into heats, countdown trigger, heat advance, and working out for itself which strip the player is standing at |
| `careerMPUIApps.lua` | re-places BeamNG's `dragRace` app so the result screen is centred and wide enough for both lanes |
| server `dragMP` relay | one enveloped event routed `all` / `host` / `{ids}`, plus **per-strip** authority election |

Two things worth recording because they were easy to get wrong:

**`shouldSyncState()` means "are we in MP", not "are we host".** `times.lua:141` assigns
it to a local named `isMP`, and `display.lua:266`'s guard is commented "in MP". If only
the host answers true, `poi.lua:65` sends every other player down the singleplayer branch
and they each start a private race. Host-only enforcement lives on the *receiving* end,
where the handlers reject anything sent to a non-host.

**Heat advance is reset-then-restart.** `dragRaceReset` clears finish times and, via
`core.onDragRaceReset`, clears `lastStartedRaceId` -- the guard that makes a repeated
`dragRaceStarted` a no-op. Only then does re-sending `dragRaceStarted` register the next
pair. core.lua says so directly: *"Allow the same raceId to trigger onDragRaceStarted
again (next heat)"*.

### What was missing, and how it was closed

All of the below is now implemented and a two-player race runs end to end. Kept here
because the shape of each problem is the useful part.

- **The lobby.** `players`, `queue`, `currentPairIndex`, `lobbyId` imply presence, pairing
  and heat progression, and none of it ships. Built in `careerMP/dragLobby.lua`: presence
  by heartbeat, arrival-ordered pairing into heats, and the "all staged → countdown"
  decision. Authority is **per strip**, elected server-side and held only while the holder
  is standing there — a session-wide host cannot work, because every decision is made by
  reading the holder's own `core.getData()`, so a host off doing deliveries has no drag
  data and nobody anywhere can race.
- **Session/race creation senders** — `dragSessionStarted`, `dragRaceStarted`,
  `dragRaceCountdownStart`, `dragRaceReset`. No gamemode method triggers these, so the
  lobby owns them.
- **`multiplayer_sessionManager`**, five functions game-wide. Note `getCurrentSession` must
  return **nil** and `isSessionHost` **false**: they mean "a BeamNG *official* multiplayer
  session", and answering otherwise switches whole subsystems onto a UI backend that does
  not ship (it replaced the career pause menu and silently disabled taxis).
- **`bridge`**, ten functions, of which only `sendToClientIds` is real work — the server
  plugin gained per-client targeting for it.
- **Clock mapping.** `os.clockhp()` is process-relative. Measured offsets between the two
  test machines: **+33.5s, +135.0s, −59.6s** across three sessions. The naive comparison is
  not slightly wrong, it is nonsense — and a *negative* offset makes elapsed time negative,
  `math.max(0, ...)` pins it to zero, and the reaction timer resolves under 0.0005, i.e. an
  automatic red-light DQ for the non-host on every single run. Currently each client uses
  its own arrival anchor (`localRaceStart` / `localCountdownStart`, which the handlers
  already record alongside the host's value). `multiplayer/synclib.lua` implements the
  proper mapping and is used for finish times only, not the race clock.

### Things that cost a test round each

The failures below all looked like sync bugs and were not. Each is cheap to avoid once
named.

- **`getDragGamemode` is a local, not a module field.** Patching `core.getDragGamemode`
  fixes `poi.lua` and nothing inside `core.lua`, so joining works while every internal
  decision still runs single-player. The sandbox blocks `debug.setupvalue`. The workable
  route is re-reading BeamNG's source, restoring their commented-out lines, and copying the
  rebuilt module over the live table.
- **Player ids as table keys do not survive JSON.** `jsonEncode` only emits an array when
  keys run `1..n`; player ids start at 0, so an id-keyed `players` map is written as an
  **object with string keys**, and `players[localPlayerId]` (a number) misses on every
  remote. Everything downstream then falls back — including a path that puts both cars in
  lane 1. Send dense arrays carrying their own `playerId`, and rebuild the maps on receipt.
- **`racers` is keyed by vehicle id, which is machine-local.** Two players can genuinely
  both be driving id 12345, collapsing two racers into one. Use a synthetic id derived from
  the player id (negative, avoiding `-1`, BeamNG's "unknown" sentinel); `core.lua` then
  swaps the local player's stub for their real vehicle, which is what it was written to do.
- **`players[playerId].lane` is load-bearing.** It gates the only path that gives the local
  player a real racer. Omit it and every racer stays a stub with no `vehObj`, so no stage
  beam is ever read and the countdown can never fire.
- **The host advances out of staging differently from everyone else.**
  `onDragRaceCountdownStart` takes neither branch for the host — the comment says the host
  advances via `checkTimerDrift` instead. Miss that and the authority stages, fires the
  countdown, and sits there with a dark tree.
- **Ordering inside that one frame matters.** The tail of `onDragRaceCountdownStart`
  unconditionally sets `phases[2].started = true`, and `display.startDragCountdown`
  discards the call if the racer is not already in phase 2 — where `racer.treeStarted` is
  the *only* assignment in the whole drag tree. Advance a frame late and the tree is dead
  permanently, with no retry (`phaseHandlers` gates on `not phase.started`).
- **`finalizeMpPostRace` exists and nothing calls it.** In MP the game hands the result
  screen to the session layer: `sendTimeslipDataToUi` raises `onDragMpTimeslipRequested`
  and returns. That hook is raised in exactly one place and handled nowhere. Answer it with
  `core.finalizeMpPostRace()` — hand-building a slip skips the win data and display signs.
- **`reset` and `clear` are opposites for the tree lights.** `core.reset` fires
  `updateTreeLightStaging, true`; `core.clear` fires it `false`. Ending a race with
  `dragBridge.reset()` switches the staging lights back on.
- **Never hand the game its own strip cache.** `getDragDataForLevel` returns entries of a
  process-lifetime cache. `setupRacerMpStub` writes every stub into
  `getLocalClientActiveRace().poiData.racers`, so aliasing that cache writes remote stubs
  into the level's own strip definition permanently — and the next race starts with a
  racers table full of stale, wheel-less stubs. `poi.lua:75` states the rule outright:
  *"Work on a local copy so the cached level data is never mutated."* Deep-copy.
- **A career drag mission is single-player.** Reporting multiplayer while one is in the
  foreground hands an AI race to code expecting network racers, and lets the lobby claim a
  strip the mission owns. `gameplay_missions_missionManager.getForegroundMissionId()` is
  the game's own test for this.
- **One `flashMessage` call fires two hooks.** `TopCenterAppsFlashMessage` and
  `ScenarioFlashMessage` are rendered by `topCenterApps` and `raceCountdown` respectively,
  and both ship in the career and freeroam layouts — so every drag message is drawn twice.
  Not multiplayer-specific, just far more visible once races actually run.
- **Lazily-loaded extensions are not loaded when you think.** A patch aimed at
  `gameplay_drag_display` at activation time silently does nothing, because that module is
  only loaded when the drag code first needs it. Load it, or defer the patch.

### Feasibility notes

- Remote vehicles are real, fully-spawned vehicles under BeamMP
  (`spawn.spawnVehicle(...)` in `MPVehicleGE.applyVehSpawn`), so registering one as a racer
  is sound. `simplifyRemoteVehicles` only swaps the model.
- The drag MP design never reads remote telemetry — each machine times its own car — so

## Never wrap a function BeamMP re-asserts

The single most important constraint found while porting, and it is not obvious.

`lua/ge/extensions/beammp/multiplayer.lua` reinstalls its overrides from its own
`onUpdate` — every frame — using this pattern:

```lua
if gameplay_walk.toggleWalkingMode ~= modifiedToggleWalkingMode then
  originalToggleWalkingMode = gameplay_walk.toggleWalkingMode
  gameplay_walk.toggleWalkingMode = modifiedToggleWalkingMode
end
```

"If the current function is not mine, capture it as the original and replace it."

That makes such a function impossible to wrap safely. Wrap it and you capture
BeamMP's function as *your* original; one frame later BeamMP sees a function that is
not its own, captures *yours* as *its* original, and reinstalls itself. The two
wrappers now call each other forever. It presents as a stack overflow somewhere
unrelated — here it killed walking mode entirely, with a traceback alternating
between `beammp/multiplayer.lua:42` and the patch module, forever.

As of BeamMP's 0.39 release, the off-limits set is:

| function | what BeamMP does with it |
|---|---|
| `gameplay_walk.toggleWalkingMode` | deletes the unicycle after entering a vehicle, so the avatar disappears for other players |
| `gameplay_walk.onVehicleSwitched` | preserves walk state across the switch |
| `core_camera.getDriverData` | corrects the mirrored driver side on remote vehicles |
| `onInstabilityDetected` | suppresses instability pausing in a session |

`gameplay_walk.getInVehicle` and `setWalkingMode` are *not* in that set and can be
wrapped normally.

Two practical rules follow. Check what BeamMP already overrides before wrapping
anything in the `gameplay_*` / `core_*` namespaces — it may already do what you
want, as with `getDriverData`, where CareerMP was carrying a duplicate of BeamMP's
own logic. And use `xpcall` with `debug.traceback`, never bare `pcall`: `pcall`
discards the stack, and the stack is the only thing that identifies a recursion.
This bug was misdiagnosed twice because the guard meant to catch it was destroying
the evidence.

## Base-game issues worth reporting to BeamNG

- `career/modules/insurance/insurance.lua` uses `invVehs[invVehId].id` where it means
  `.insuranceId`. Present in both 0.38.6 and 0.39; affects single player too.
- `career/modules/vehicleShopping.lua` `spawnVehicle` never checks the return of
  `core_vehicles.spawnNewVehicle`, then immediately indexes it. **Mostly defused in
  0.39.1**, which gated `canSpawnAnotherVehicle()` behind a PS5 platform check so it
  always returns `true` on PC — the patch notes describe this as "the system will no
  longer refuse to spawn additional vehicles or traffic when running out of memory".
  Before that, a machine under ~1 GB free RAM would hit `attempt to index local 'newVeh'
  (a boolean value)` — a fatal Lua error in the middle of a purchase. The unchecked
  return is still there, so any other path that makes `spawnNewVehicle` return early
  (a config that fails to prepare, e.g. a removed mod vehicle) reaches the same crash.
- `gameplay/walk.lua` `getInVehicle` captures the unicycle reference *before*
  `be:enterVehicle` and uses it after, so anything that destroys the unicycle during the
  switch causes a fatal "object that no longer exists" at line 90. Not reachable in
  single player; reachable in multiplayer, where the walking avatar is a synced vehicle
  that can be despawned on entering a car. Seen live both when buying a vehicle
  (`vehicleShopping.lua:591`) and when pressing enter beside a car
  (`toggleWalkingMode` → `setWalkingMode` → line 149). One line to fix upstream: read
  the id before the switch, or re-resolve after it.

  Worth noting for anyone patching around it: line 149 calls `getInVehicle` as a
  **file-local**, not through the module table, so replacing `M.getInVehicle` does not
  intercept it. The traceback distinguishes the two — `Lua upvalue 'getInVehicle'` for
  the internal call, `Lua field 'getInVehicle'` for the external one. Covering both
  means guarding every module entry point that can reach the internal call site.
- `freeroam/bigMapMode.lua` assumes the sim is paused while it is open
  (`simTimeAuthority.pushPauseRequest("bigMap")`). BeamMP no-ops pause requests in a
  session, so that assumption does not hold in multiplayer. Not currently harmful,
  because the big map's visible sky change is cloud cover and fog (both set to 0 on enter
  and restored on exit) rather than time of day — no level ships a `bigMapTimeOfDay`, so
  `bigMapTod` falls back to the entry time and the ToD transition is a no-op.
